# Visor + Claude Code bridge (Claude subscription on the glasses)

How this fork of [Visor](https://github.com/macedonga/visor) answers "Hey Meta" with a Claude Pro/Max subscription instead of an API key. A small HTTP bridge on the phone turns Visor's OpenAI-style requests, tool calls included, into questions for a Claude Code process. Notes and findings from the 2026-10-27 and 2026-10-28 work are at the end.

## Architecture

```text
Ray-Ban Meta glasses ──Bluetooth──> Visor (Android app)
                                       │  OpenAI-compatible request, http://127.0.0.1:8080/v1
                                       ▼
                         bridge.js  (Termux > Ubuntu proot, Node)
                                       │  stream-json over stdin/stdout, one warm process
                                       ▼
                         claude -p  (Claude Code, logged in with the subscription, model haiku)
```

- Visor answers every wake phrase ("Hey Meta", a custom "Hey Jarvis") with one configured model. It plays Meta's assistant server on the glasses' link, so there is no per-phrase choice and no hand-off to Meta's own AI.
- The app has three providers: **Claude API** (Anthropic key), **Claude subscription** (this bridge) and **OpenAI-compatible** (anything else). The subscription tab is the OpenAI-compatible path with the bridge's address and model filled in.

## Setup on the phone

Step by step in [SETUP.md](SETUP.md). The author's phone also has a private `control.sh {start|stop|status}` (PID file, for starting by hand) and older bridges as `bridge.js.bak` and `.v2` to `.v6`; none of that is needed.

## The Visor side (changes in this fork)

- `Provider.CLAUDE_SUBSCRIPTION` in `Brain.kt`, handled like OpenAI-compatible in `Brain.kt` and `Models.kt`; `SettingsScreen.kt` and `MetaAiScreen.kt` treat any non-Claude-API provider as configured without a key.
- `AssistantSettings.kt`: three provider pills; picking the subscription sets the model to `claude-code` and the server to `http://127.0.0.1:8080/v1` unless the address already points at this phone. A **Bridge** row on that tab shows the status ("Running in Termux." when `/v1/models` answers), a note that the subscription only works while the bridge runs, and one button: Allow, then Start or Stop. After a tap a spinner stands in for the button until the bridge answers, or stops answering (checked every 0.75 s, up to 15 s), instead of a fixed 6 s. The tab hides what the bridge ignores: base URL, API key, model, diary model, the conversation memory window and custom instructions (the bridge picks its model and keeps its own conversation; Visor's system prompt apart from memories does not reach it). To set `BRIDGE_TOKEN` as a key or another address, use the OpenAI-compatible tab.
- `TermuxBridge.kt`: the button's work. Termux's `RUN_COMMAND` service runs `proot-distro login ubuntu -- bash -c "cd /root && exec node bridge.js >> bridge.log 2>&1"` to start, and `pkill -f "node bridge.js"` to stop. The manifest adds the `com.termux.permission.RUN_COMMAND` permission and a `<queries>` entry for `com.termux`.
- `Vision.kt`: a question whose glasses intent names an image (`IMPLICIT_DESCRIBE_IMAGE`, "what can I cook with this") now asks for the photo. It set none of the glasses' image flags and none of the word list, so before this no photo was requested and the model said it saw no image.
- `open_app` in `Phone.kt` and `PhoneActions.kt`: a tool that opens an installed app by its name ("open Spotify"). It looks among the apps with a launcher; the same name wins, else the closest one whose name contains what was said, and what was said may contain an app's name only from four letters up (an app called X once opened for "Zorbax"). Opened through the same path as directions, so while Visor is not in front, or the phone is locked, the app waits in a notification.
- `where_am_i` in `Phone.kt` and `PhoneActions.kt`: the town the phone is in, from the gallery's location code (`Places.kt`, with a 5 s limit on a new fix) and the platform geocoder, so "what's the weather here" can search the right place.
- `weather` in `Phone.kt`, with `Weather.kt`: now, today and tomorrow from Open-Meteo (free, no key). It uses the phone's coordinates, or Open-Meteo's geocoder when the wearer names a town; nothing else leaves the phone. The bridge prompt tells Claude to use it rather than search.
- `Greeting.kt` (new, in `metaai/`): Settings > Meta AI > **Greeting**. When the glasses go back on after being off (or out of reach) for at least 15, 30, 60 or 120 minutes, the phone's text-to-speech says the greeting ("Welcome back boss" by default, editable; the comma made a pause) through the glasses as Bluetooth audio, with the music ducked. It watches `device.worn` (the glasses' DON/DOFF) from `GlassesService`; the glasses' own voice is only for answers to a question they opened, so an unasked greeting cannot use it. **Try the greeting** plays it at once. Heard through the glasses on 2026-10-29; the wearer found the phone's voice next to the glasses' own voice odd. A **Glasses** voice was tried and removed: sending the greeting as an incoming WhatsApp-style chat message from the wake word's name ("Jarvis"), the kind the notification mirror sends. The glasses took it (each one answered on svc46 with a type 2, 86 bytes, meaning unknown) and, phone locked or not, played their notification sound but read nothing out. The greeting waits 3 s after the glasses come on, so their power-on sound does not cover it.
- `read_notifications` in `Phone.kt`, with `notify/Unread.kt` (new): the phone's current notifications, newest first, one line each ("WhatsApp, 5 min ago: in Family, Ana: are you coming?"), optionally from one app. Leaves out Visor's own, Termux's, running and foreground ones, group summaries and silent ones; unlike the glasses' mirroring it keeps SMS. It reads them from Visor's notification listener (`MirrorListener.current`), so it needs the notification access Visor already asks for. First try on the glasses (2026-10-29): "any notifications" got "no new notifications" with two Telegram chats on the phone, because Haiku called the tool with `app: "all"` and no app has that name (the tool logs "Phone: Notifications from …" with what it found). "all", "any", "everything" and the like now mean every app, and the field's description says to leave it out unless an app is named. After that it read the Telegram chats on the glasses.
- `Assistant.kt`: when the model ends the conversation, nothing is spoken; the glasses just stop listening (the farewell was "You're welcome.").
- Strings in English, Italian and Russian.

Keep fork changes in these few places (and new files) so `git merge upstream/main` stays quiet.

## The bridge (`bridge.js`)

- **One warm process**: a long-lived `claude -p --input-format stream-json --output-format stream-json` answers every question, so Claude Code does not start per request. It restarts after 10 idle minutes (`BRIDGE_IDLE_MIN`), 40 turns, an error or a 40 s timeout, and starts again right away.
- **Model picker** (1.3): the subscription tab has Haiku, Sonnet and Opus pills instead of the model field. Visor sends the choice as the request's model; the bridge restarts the warm process when it changes (a fresh conversation) and tells it which model it is, so the tab's **Test the connection** (the old Try it, asking for a hello and the model's name) shows it. An older `claude-code` means the default. Only one process runs: switching ends the old model's process, so there are never three sessions, and going back to a model does not bring its conversation back. Remembered facts come from Visor and reach every model. With the bridge up, picking another model asks first ("Claude starts a new conversation…"); the test row shows only while the bridge runs. On the Mac: switching cost about 0.5 s, and Sonnet answered in about 1.6-2.1 s like Haiku for a short hello.
- **Resume** (1.3): a switch on the subscription tab, sent to the bridge inside the model setting (`haiku;resume`) so Visor's core needs no new field. **Resume conversations** keeps each model's conversation on disk (no `--no-session-persistence`), notes its session id in `~/.visor-bridge/sessions.json`, and starts the model with `--resume <id>` after a switch back, a bridge restart or the idle time; 40 turns, an error or "clear session" still start fresh. With it on, switching models does not ask first. On the Mac: Haiku was told a favourite colour, Sonnet did not know it, Haiku knew it again after switching back and after a bridge restart, each answer 1.5-1.9 s. A **Remote Control** switch (`--remote-control "Visor glasses"`) was tried and removed before the commit: on the Mac it answered normally, but on the phone (2026-10-29) no "Visor glasses" session showed up in claude.ai/code, so in print mode the flag does nothing visible. Resume worked on the glasses: a number told before a model switch was remembered after switching back.
- **Name from the wake word** (1.3): the transcript starts with the wake phrase ("hey jarvis what's..."), so the bridge takes its word as the assistant's name and tells the warm process once, and again when the wearer uses another word. Asked its name it says "Jarvis"; asked its model, just "Claude Haiku" (a later build dropped "made by Anthropic"). A question without the wake phrase (a tap on the glasses, a follow-up) uses the last name, which is kept in `sessions.json` across restarts; until "hey <name>" was said once, there is none. On the glasses (1.3.1, 2026-10-29) it failed twice over: the questions came from a tap, so no name was known, and the resumed conversation held older "made by Anthropic" answers, which Haiku repeated. 1.3.2 keeps the name and tells it never to say who made it, but on the glasses a tap still got "I'm Claude, made by Anthropic": no wake phrase had been said, so no name was saved, and the resumed conversation still held the old answers. 1.3.3: Visor adds the glasses' custom wake word (the wake word screen's saved `enrolled`, read when the subscription tab opens) to the model setting as `name=Jarvis`, so a tap gets that name; a different word said aloud still wins. The phone's `sessions.json` was deleted to drop the old conversation. on the Mac, after one "hey jarvis" and a restart, "what's your name" gave "Jarvis." and "what model are you" "Claude Haiku." On the Mac: "hey jonathan what's your name" gave "I'm Jonathan…". "Hey Meta" makes it Meta. Conversation files pile up in `~/.claude/projects` in the proot while resuming is on.
- **Flags**: default model `haiku` (`CLAUDE_MODEL`), a short voice system prompt, `--tools WebSearch --allowedTools WebSearch` (web search only, for current facts), `--strict-mcp-config`, `--disable-slash-commands`, `--setting-sources ""`, `--no-session-persistence`, run from `~/.visor-bridge`.
- **Context**: the process remembers the conversation until it restarts. Saying "clear session" (or `/clear`) restarts it. Only Visor's last user message is used; of Visor's system prompt only the memories part (below).
- **Tool calls**: Visor's tool declarations (music, memory, MCP servers) are listed for Claude once per warm process, and again only if the list changes. Claude answers with one line, `TOOL_CALL {"name": ..., "arguments": {...}}`; the bridge turns it into an OpenAI `tool_calls` reply, Visor runs the tool, and the result goes back to the warm process as `TOOL_RESULT <name>: ...`. A call naming a tool Visor did not offer is spoken as text instead. After 4 results in a row for one question the list is withheld so the model must answer.
- **Memories** (1.2.0): Visor keeps facts the wearer asked it to remember and lists them in its system prompt, which the bridge otherwise ignores, so before 1.2.0 Claude could save facts but never saw them later. The bridge now cuts the memories part out of that prompt (from "You can keep lasting facts" to the next part Visor adds) and gives it to the warm process once, and again whenever it changes, as after a `remember`. On the Mac with two made-up facts: "where did I park" and "when is my sister's birthday" were answered from them, and "remember that my dentist is doctor Huber" called `remember`, each in about 1.6 s. Tried on the glasses on 2026-10-29: remembering a fact and recalling it later worked. The cut depends on Brain.kt's wording.
- **Vision**: `image_url` data URLs become Claude image blocks. No temp files and no Read tool.
- **No shell**: questions never touch a command line, so spoken `$(...)` or backticks run nothing (the first bridge built a shell string from the question).
- **Ending a conversation**: the prompt asks Claude to judge by meaning whether the wearer is closing the conversation ("thanks", "aight thx", "nvm", "nah I'm good", "ok bye"), not by a phrase list, and then to end its answer with `END_CONVERSATION`. The bridge strips the marker and, if Visor offered `end_conversation`, answers with that tool call. Visor then asks once more with a `tool` message; the bridge answers that from the earlier text without calling Claude. Visor sends the glasses the reply without the follow-up flag, so they stop listening. Since 2026-10-29 Visor speaks nothing then (the short farewell was dropped).
- **Clipped words**: the glasses' recogniser often drops the first word of a follow-up ("and times two" heard as "n times two"). The prompt tells Claude to read such fragments as follow-ups to its last answer.
- **Auth**: optional `BRIDGE_TOKEN`; use the same value as Visor's API key. Other apps on the phone can reach a loopback port, so set it if that matters.
- **Messages read out by the glasses**: Visor's settings search "Messaging app settings" (the glasses' `assistant_comms_provider_settings_protobuf`) holds one card per messaging app with Enabled, Announce new messages, Read messages out, Reply by voice. Visor forwards every chat app (Telegram too) as WhatsApp, so the WhatsApp card decides; it was Enabled off, which left the glasses silent. Set to Enabled, Announce and Read out on 2026-10-29. Changes go out with **Save to the glasses** at the bottom. The App pills on a card used to change which app the card is for; since 2026-10-29 an entry whose app is set shows it as the card's title instead (`StructuredEditor.kt`, for any list whose entries start with a choice), and only a newly added entry offers the pills. Named entries start folded: the app's name and the switches that are on ("Enabled · Announce new messages · Read messages out"), unfolding on a tap.
- **Version**: `VERSION` at the top of `bridge.js`, as major.minor.patch: the minor number goes up once per commit, the patch number with each build tried on the phone between commits (1.0 the warm bridge with tools, 1.1 web search and the weather prompt, 1.2 memories, 1.3 the model picker, resume and the wake word as name). `/v1/models` names the model "Claude Code, bridge 1.3.1", and Visor's Bridge row shows that next to "Running in Termux.", so it is clear which copy the phone runs.
- Env: `BRIDGE_PORT` (8080), `CLAUDE_MODEL`, `BRIDGE_TOKEN`, `BRIDGE_IDLE_MIN`.

## Findings

**Speed.** Old bridge (`claude -c -p` per request, default model, long default prompt): 7-12 s from the glasses' question to the answer. Now: about 1.4-2.0 s for the model on the phone, 0.8 s on the Mac with the same bridge. Overall about 5 s from "Hey Meta", because the glasses spend about 3 s recording and recognising. Sending the tool list with every question cost about 0.3 s on the phone; sending it once per process fixed that on the Mac, but the phone's median stayed near 1.9 s, so the phone side is the limit. With the phone's voice, answers take longer since the speech is made on the phone.

**Web search.** The bridge lets Claude use Claude Code's WebSearch tool, and the prompt limits it to current or local facts. On the Mac (2026-10-29): "two plus two" took 1.4 s with no search; "weather in Lisbon right now" took 11 s and gave a hedged answer; "most recent F1 race" took 20 s and was right. So a search costs 10-20 s, within the bridge's 40 s timeout. On the glasses (2026-10-29, Haiku), from the transcript to the spoken answer: "what's the weather here today" took 2.4 s and did not search, because the model does not know where the wearer is (it asked for the city). "Who won the last F1 race" took 11.3 s, searched, and said the results conflicted. The glasses waited the whole 11 s. Visor's assistant has no location tool, though the app already holds the location permission for photos. Haiku's searches were weaker on the phone than on the Mac for the same question. With `where_am_i` the weather question found Sankt Pölten but the search still gave no forecast (12 s, "results were from other dates"): web search is the wrong tool for weather. Hence the `weather` tool below. With it (2026-10-29): "what's the weather here today" 8.0 s (the first question after a bridge restart, so the tool list went with it), "Lisbon" 3.8 s. "Will it rain tomorrow in Lisbon" was heard by the glasses as "in wis", so Claude answered for Sankt Pölten and asked which place was meant; the glasses' recogniser, not the tool.

**Instructions are not repeated per question.** The voice-assistant prompt goes in once with `--system-prompt` when the warm process starts, and the tool list once per process; each question sends only its own text. The API still receives the whole conversation on every turn, but the unchanged start (system prompt, tools, earlier turns) is served from Claude's prompt cache at a fraction of the cost and time. Repeating the instructions in every question would add tokens and nothing else. The prompt is re-sent only when the process restarts (10 idle minutes, 40 turns, an error). Saving it in Claude's memory (CLAUDE.md) would not help: `--setting-sources ""` keeps files like that out on purpose, and the system prompt already does the job. Not measured: actual token use per question.

**Where the time goes (2026-10-29, bridge 1.4.x).** A tap question on the glasses: about 3.2 s from the tap to the transcript (speaking plus the glasses' end-of-speech wait and recognition), then 1.9 s to the answer, then speech. Of the 1.9 s, Visor takes under 0.1 s; the bridge log's breakdown (1.4.1 logs Claude Code's own time and its API time per turn) showed on the phone, for seven questions, Claude Code 1.5-1.8 s of which the API 1.45-1.74 s: about 93 % is waiting on Anthropic, with the prompt cached (cache read about 2,000 tokens, write under 100, 5-15 tokens out). The gap between questions (1, 6 or 20 s) changed nothing, so connections and the cache stay warm. On the Mac the same API time ran from 0.7 s to 2.9 s per answer between runs of the same questions, so it varies on Anthropic's side; dropping the WebSearch tool made no clear difference, and thinking is not on. Claude Code made an extra background API call with each new process's first question; `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1` (1.4.2) stops it, with no measurable change in time. Visor does not stream and the glasses take the answer as one text, so speaking before the model is done would need protocol work. **Closed (1.4.3):** with Quiet after actions on, an action that worked ("open Spotify") still waited for a second model reply that was then not spoken; Visor now ends the turn after the tool when every call in the round was an action that worked, and the bridge closes the waiting call ("TOOL_RESULT open_app: done.") on the next question. On the Mac, after a skipped result, "did you open spotify" got "Yes, I opened Spotify on your phone." On the glasses (2026-10-29): Spotify opened 2.1 s after the question and the turn was over 0.15 s later, at 2.2 s. **Still open:** the glasses' end-of-speech wait (no setting for it found), and the glasses' speech speed (Speech speed, 1.25x or more, shortens every answer).

**Follow-ups.** They chain only with the glasses' own switch **Respond without "Hey Meta"** on (`assistant_follow_up_enabled`). Visor's **More follow-ups** feature (MobileConfig flags) is separate and needs a glasses restart. With the follow-up switch on, the glasses open a new listening turn about 0.1 s after each answer (wake type 5) and close it themselves after 7 to 20 s of silence. Visor sends the follow-up flag for both voices; the glasses' own voice works with it on this pair. No setting for the length of that window was found; the MobileConfig flags `assistant_on_sn.default_asr_timeout_s` and `assistant_shutdown_waiting_interaction_loop_count` are candidates, untried.

**Wake phrases.** The glasses' transcript includes the wake phrase ("hey jarvis what's three plus three"), and the interaction start lists the custom phrase in both cases, so a phrase can only be told by the text. A custom wake word ("Hey Jarvis") is learned on the glasses in Settings > Meta AI > Custom wake word. Both phrases reach the same model.

**The custom wake word needs the US language pack.** After the glasses took the UK English pack (en_GB, voices `en_GB.0` and `.1`) and were closed and reopened, "Hey Jarvis" stopped waking them, and teaching it again failed with "Audio processing failed: resource 'audio_engine_voice_cww.json' not found". It worked again after going back to US English. Jarvis kept working for about ten minutes after the UK pack was sent, until the restart, which fits the glasses loading the new files at boot. That the UK pack lacks the file is an inference, not confirmed. Visor shows the word as set from its own saved state, not from the glasses.

**Stopping an answer.** A long press on the side button already stops the glasses' voice, and the glasses do it themselves. In the log it shows as a new, bare interaction (`2=3, 3=4`, no wake audio) that the glasses close within 0.1 s, and the interaction that was speaking ends with reason **17** (it was replaced). Normal ends are 12, and 16 showed up with the glasses handling something themselves. Answering the bare interaction as Meta's server does in Live AI (creation success, server connection status twice, `AsrStartListening`) did not make the glasses listen, so that experiment was removed. To ask something right after stopping, say the wake phrase again. A single click on the side runs the glasses' own media action (it resumed Spotify).

**Speed and voice of the glasses.** Visor's Settings > Language and voice has **Speech speed** for the glasses' own voice (0.75x, 1x, 1.25x, 1.5x, 1.75x, `tts_speak_speed`). The voice list (`assistant_voice_id`) holds Meta's voices only: Aria, Helio, celebrity and Italian ones, plus the British ones with the UK pack. A custom voice is possible only for the phone's voice, which is Android text-to-speech; Visor has no picker for the engine voice yet.

**Photo questions.** With the `Vision.kt` change, "what am I holding" and "what can I cook with this" request the photo and the model describes it. If the warm process remembers an earlier photo, a vague question such as "tell me about the roses" can be answered as if it were about that photo; "clear session" or a clearer question avoids it.

**Tools work through the bridge.** "Play some jazz" ran Visor's music tool and Spotify resumed once it had a media session. Before that Visor answered that the phone needed an app to play from, which was a Visor setting and the missing session, not the bridge. A Home Assistant tool is not set up in Visor, so "turn off the light" has nothing to call.

**Open apps by voice.** "Open Spotify" and "open WhatsApp" opened the apps in about 1.2 s from hearing the question; "open Zorbax" said there is no such app and opened nothing. The first version opened X for "Zorbax" because the word contains the letter x; the four-letter rule above fixed it. Visor's own `play_media` matching for music apps still uses the looser rule. With the phone locked (or Visor not in front) it did not open the app but left a notification: the log shows "Phone: Waiting in a notification: Open Spotify" at 18:32:41, and tapping it opened Spotify.

**Quiet after actions.** The Visor switch Settings > Meta AI > **Quiet after actions** (`quiet_after_actions`, off by default) makes the glasses say nothing when every tool did what was asked. With it on, "open Spotify" and "open WhatsApp" ended with "Ended the turn without a word: every tool did what was asked" in the log, a plain question was still answered aloud, and a failed action still speaks. A reply that ends in a question is also spoken. It is all or nothing; a per-request "tell me when it's done" would need a Visor change.

**Remote Control.** Claude Code's Remote Control is Anthropic's relay between a session on your machine and claude.ai or the Claude mobile app. No supported API lets another program join a session by ID, so the glasses cannot attach to the Home Jarvis session on the Pi. `claude --resume <id>` works only on the machine that holds the conversation file, and Home Jarvis runs inside the Claude Terminal Pro add-on, which publishes no port. House control would have to come from Home Assistant's own MCP server added in Visor, not from that session.

**Remote Control and the bridge.** `claude --help` (2.1.303) lists `--remote-control [name]` as starting an *interactive* session. A `-p` stream-json run with `--remote-control visor-test` on the Mac (2026-10-29) answered normally and printed nothing about Remote Control, so print mode, which the bridge needs, does not seem to take part; whether a "visor-test" session showed up in claude.ai/code was not checked. Resuming a conversation is possible: dropping `--no-session-persistence` keeps it on disk, and `--resume <session-id>` (the id is in the `init` and `result` events) starts a process on it.

**Meta's own AI is out of reach.** With Visor as the assistant, nothing hands "Hey Meta" to Meta's real assistant. Doing it would mean Visor calling Meta's private backend with the Meta login: unsupported, fragile, and a terms risk. Using Meta's AI means the Meta app owns the glasses again, which stops Visor.

**The proot kills what it started.** A bridge started inside a proot session dies when that session or command ends. That is why the app's Start runs Node as the command itself, and why starting it by hand only works while the Ubuntu shell stays open.

**Tried on the phone and glasses.** Text answers, follow-ups, "thanks" and other closings, music, photo descriptions, opening apps by name, quiet after actions, the three provider tabs and Try it, the Bridge row status, Start keeping the bridge up for minutes. Not tried: the Home Assistant route, the 10-minute idle restart, Start from the background.

## Troubleshooting

| Symptom | Cause and fix |
|---|---|
| Glasses say "Sorry, I couldn't get an answer", log has `401 invalid x-api-key` | Provider is Claude API, so Visor called api.anthropic.com. Pick Claude subscription. |
| Same message, nothing in the bridge log | Bridge not running. Check the Bridge row, or `curl http://127.0.0.1:8080/v1/models` in Termux. |
| Bridge died after leaving the Ubuntu shell | See "The proot kills what it started". Use the Start button. |
| The glasses say "make sure Meta AI is active and Bluetooth is connected" | Visor's link to the glasses is down (log: "Link: lost them", "reaching the glasses"). Open Visor, wait for Home to show them connected, and ask again. |
| "Hey Jarvis" does nothing, "Hey Meta" works | The custom word needs the US language pack; see the finding above. Switch back to US English, restart the glasses, teach the word again. |
| Follow-up not understood ("n times two") | First word clipped by the glasses' recogniser. Pause half a second after the answer; the prompt already reads such fragments as follow-ups. |
| No follow-up listening at all | Turn on Respond without "Hey Meta" under Settings > Meta AI. |
| Music does not start | Start something in Spotify first so it has a media session, and choose it in Visor's media settings. |
| "Open <app>" says there is no such app | The name did not match an app with a launcher; say it as the app is labelled on the phone. |
| "Open <app>" only shows a notification | Android lets Visor open another app only while Visor is in front (or as a companion app); tap the notification. |
| Start does nothing | Termux needs `allow-external-apps = true` and Visor needs the Allow grant. |

## Working on the fork

- `upstream` is `macedonga/visor`. Merge often: `git fetch upstream && git merge upstream/main`. The last merge (2026-10-27) had no conflicts. Don't delete upstream files; keep additions in new files.
- Debug builds: `./gradlew :app:assembleDebug`, then `adb install -r app/build/outputs/apk/debug/app-debug.apk`. Logs: `files/events.log` through `adb exec-out run-as com.macedonga.visor cat files/events.log`. `files/wire.log` is encrypted frames, so it does not help with unknown messages.
- Test on the Mac first: `bridge.js` runs there with the `claude` CLI (`BRIDGE_PORT=18080 node bridge.js`, then curl `/v1/chat/completions`, with a `tools` list to try tool calls).
- A foldable has two displays: `adb exec-out screencap -p -d <id>`. The same phone can appear twice in `adb devices`, or under a different name after reconnecting wireless debugging; use `-s`.
- Glasses behaviour is only proven by trying it on the glasses. Commit after the wearer has tried a change.

## Not done

- Per-phrase routing ("Hey Jarvis" to a different persona or model). Possible by matching the transcript prefix; dropped for now.
- Starting the bridge on demand when a question arrives and it is down (Android limits starting other apps' services from the background).
- Home Assistant as a tool: add its MCP server in Visor's integrations (expose only safe entities; locks and alarms stay out).
- Interrupt and listen with one press; a shorter follow-up listening window (the two flags above).
- A voice picker for the phone's text-to-speech, a chess helper (Stockfish plus a board-reading step).
- A relay to Meta's real assistant.
